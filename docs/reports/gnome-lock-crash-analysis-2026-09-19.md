# 화면 잠금 해제 후 GNOME 세션 종료 분석

분석: 2026-09-19, 한국 시간. 시스템: Ubuntu 26.04.1, Wayland, GNOME Shell 50.1-0ubuntu1.2, Mutter 50.1-0ubuntu2.2.

## 결론

08:55:28에 GNOME Shell PID 68591이 SIGSEGV로 실제 종료됐다. 덤프에서 확인한 직접 원인은 `xkb_keymap_mod_get_index()`에 전달된 NULL 키맵이다. 호출한 Mutter 코드와 공식 수정 내용을 대조하면, **입력 스레드가 키맵을 교체하는 동안 메인 스레드가 같은 키맵을 읽는 경쟁 상태**가 매우 유력하다. Ubuntu 버그 [2152175](https://bugs.launchpad.net/bugs/2152175)의 호출 경로 및 동일 버전 보고와 일치한다.

사용자는 지문으로 잠금을 해제했다고 확인했다. 지문 인증이 끝나면서 데스크톱의 입력기 상태를 복원하는 과정이 이번 버그의 촉발 조건으로 보인다. 지문 센서 드라이버 자체가 GNOME을 충돌시켰다는 근거는 발견하지 못했다.

| 08:46:37 | 관리자 지문 인증 설정을 적용하기 위한 기존 비밀번호 인증 시작. 완료되지 않고 대기 |
| 08:55:26 | 잠금 화면에서 fprintd 시작 |

시스템은 02:51부터 같은 부팅 상태였으며 재부팅된 것이 아니다. 조사 중 현재 세션은 유지됐고, systemd 시스템·사용자 실패 서비스는 없었다.

## 덤프의 구체적인 증거

Apport 기록 `/var/crash/_usr_bin_gnome-shell.1000.crash`의 CoreDump를 로컬에서 추출하고 GDB로 분석했다. 재현을 위해 현재 세션을 잠그거나 종료하지 않았다.

GNOME의 자체 신호 처리기를 제외한 실제 오류 경로:

```text
xkb_keymap_mod_get_index()                 libxkbcommon
Mutter +0x1b4903                          update_state_from_modifier_state와 대응
Mutter +0x1b49fd                          update_keymap_in_main과 대응
GLib main loop
```

Mutter 내부 함수명은 해당 버전 소스·기계어 및 동일 버전의 공식 버그 보고를 대조해 식별했다. 설치된 Mutter와 일치하는 디버그 심볼은 공식 서버에서 내려받지 못했으므로, 로컬 역추적 자체의 해당 두 프레임에는 함수명이 표시되지 않았다.

- 오류 명령: `xkb_keymap_mod_get_index+28: mov (%rbx), %rdx`.
- 오류 시점의 `rbx = 0`: 첫 인수인 키맵이 NULL이었다.
- 조회하려던 수정 키 이름은 `Mod2`였다.
- 호출자 기계어는 키맵 객체의 `+0x20` 필드를 읽어 이 인수로 넘긴다.
- 코어가 저장될 때 같은 필드에는 이미 `0x702c6c31a860`이라는 새 포인터가 들어 있었다. NULL을 읽은 순간과 신호 처리 후 덤프 저장 시점 사이에 값이 바뀐 증거로, 키맵 교체 경쟁 상태와 강하게 부합한다.
- 원본 50.1 소스는 입력 스레드에서 `g_clear_pointer(&keymap->impl.keymap, xkb_keymap_unref)` 후 새 키맵을 넣고, 메인 스레드는 이 필드에 동기화 없이 접근한다.

GNOME 공식 [수정 커밋 709ef343](https://github.com/GNOME/mutter/commit/709ef34381e51e83327b9c6d7270ed437d714768)은 메인 스레드의 XKB 키맵 접근을 없애고, 입력 스레드에서 계산한 결과만 전달하도록 바꾼다. 따라서 단순히 NULL 검사를 추가하는 것보다 원인에 맞는 수정이다.

## 한글 입력기와 이전 사용 경험의 관계

현재 입력 소스는 `xkb:kr+kr104`와 `ibus:hangul`이다. 설치된 GNOME Shell의 실제 내장 JavaScript를 확인한 결과:

1. 비밀번호 입력 문맥에서는 IBus 입력 소스를 잠시 제외한다.
2. 일반 입력 문맥으로 돌아오면 IBus를 복원하고 입력 소스를 다시 읽는다.
3. 키보드 관리자는 필요할 때 Mutter의 `set_keymap_async()`를 호출한다.

이 경로 때문에 잠금 화면과 데스크톱 사이의 전환은 키맵 교체를 유발할 수 있다. 사용자가 과거 Ubuntu에서도 같은 시점에 키보드 관련 크래시를 겪었다는 경험과 부합하는 설명이다. 다만 과거 버전의 덤프가 없으므로 과거 문제까지 동일한 버그였다고 확정하지 않는다. 한글 설정 자체가 잘못됐다는 증거도 없다.

## 커스텀 설정 및 다른 원인 검토

| 후보 | 이번 조사 결과 |
|---|---|
| 세손가락 드래그 | 커스텀 libinput과 shim은 로드돼 있었다. 실제 오류 스택은 두 라이브러리를 거치지 않으며, 기본 Mutter의 알려진 키맵 오류와 일치한다. 이번 크래시의 직접 원인으로 지목할 근거가 없다. |
| 지문 드라이버 | 인증 직후 크래시가 발생했으나, fprintd 크래시 기록은 없다. 오류는 별도 프로세스인 GNOME의 키맵 처리에 있다. |
| 관리자 인증 PAM 변경 | 아직 적용되지 않았다. `/etc/pam.d/sudo`, `sudo-i`는 원본이며 `/etc/pam.d/polkit-1`도 없다. 대기 중 인증 실패는 세션 크래시 이후의 결과다. |
| GPU·메모리 부족·절전 | 크래시 직전 확인 구간에 GPU hang/reset, OOM 종료, suspend 기록이 없다. NULL 키맵 오류라는 직접 증거가 있다. |
| 일반 XKB 경고 | 최대 키코드·중복 수정 키 경고는 새 정상 세션에도 나타난다. 이 경고만으로 이번 크래시 원인을 설명할 수 없다. |
| 이전 03:48 크래시 | 당시 SIGSEGV 로그는 남아 있으나 Apport 파일이 최신 사건으로 갱신됐다. 이전 사건이 이번과 동일한 원인이었다는 결론은 내리지 않았다. |

## 수정 제공 현황과 다음 조치

2026-09-19 조회 결과, [Launchpad의 Ubuntu Resolute 항목](https://api.launchpad.net/1.0/bugs/2152175/bug_tasks)은 중요도 High, 상태 Triaged였다. Ubuntu 26.10 계열 항목은 Fix Released이고 수정 버전 기록은 `51~alpha-0ubuntu2`다. 이를 Ubuntu 26.04에도 수정 배포가 완료됐다는 뜻으로 해석하면 안 된다.

현재 APT 후보 `50.1-0ubuntu2.4`는 30% 단계적 배포 중이다. 해당 버전 변경 이력과 Ubuntu 원본 Debian 패치 묶음 30개를 확인했으며, 이 키맵 파일이나 수정 커밋을 반영한 패치는 없었다. 따라서 대기 중인 Mutter 업데이트만으로 이번 문제가 해결된다고 볼 수 없다.

실질적인 해결 방향은 공식 수정이 포함된 26.04 업데이트를 사용하거나, 위 공식 패치를 현재 26.04 Mutter에 백포트해 별도로 검증하는 것이다. 원인이 확인된 만큼 세손가락 드래그나 지문 기능을 먼저 제거할 근거는 약하다. 비밀번호로 잠금을 해제하더라도 입력기 복원 경로를 거칠 수 있으므로 이를 확실한 우회책이라고 보장하지 않는다.

공식 패치를 Mutter 50.1의 해당 원본 파일에 적용하는 dry-run은 충돌 없이 통과했다. 이는 패치 적용 가능성 확인이며, 수정 버전의 빌드·실행·잠금 해제 시험을 수행했다는 뜻은 아니다.

이번 작업은 원인 분석까지 수행했다. 시스템 패키지·PAM·입력기 설정을 변경하지 않았으며, 크래시 덤프는 외부에 전송하지 않았다. 분석 자료는 작업 폴더의 `work/gnome-crash-20260919-0855/`에 보관했다.

후속 작업: 사용자의 패치 요청에 따라 같은 날 공식 수정을 백포트한 Mutter 패키지를 설치했다. 검증·적용 상태와 원복 방법은 [패치 설치 보고서](./mutter-keymap-fix-installation.md)에 기록했다.
